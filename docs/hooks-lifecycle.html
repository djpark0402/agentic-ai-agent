Claude Code Hook 라이프사이클

agentic-ai-agent 프로젝트의 자동화 정책을 단계별로 살펴봅니다

STEP 1 / 8 · 개요

훅(Hook)으로 엮는 개발 자동화

Claude Code가 제공하는 7가지 라이프사이클 이벤트에 스크립트를 연결해 git·lint·보안·컨텍스트를 자동 관리합니다.

왜 훅인가?
Claude에게 "매번 해줘"라고 지시하는 것은 불완전합니다. 훅은 harness(런타임)가 직접 실행하므로 Claude의 실수·망각과 무관하게 규칙이 강제됩니다. 커밋 메시지 한글화, 브랜치 보호, .env 차단 같은 것은 메모리가 아니라 훅으로 구현해야 합니다.

이 프로젝트에서 훅이 담당하는 4가지 영역

1
Git 브랜치 전략 — 보호 브랜치 차단 + 세션 브랜치 지연 생성 + 자동 커밋
2
.env 파일 접근 제어 — permissions.deny + PreToolUse 인라인 차단 이중 방어
3
컨텍스트 압축 복구 — PostCompact로 핵심 규칙 재주입
4
TDD · Lint 강제 — PostToolUse / Stop에서 ruff · eslint · tsc 실행
STEP 2 / 8 · SessionStart

통합 브랜치 준비 (session-start.sh)

CLI 최초 기동 시 1회만 실행 — 세션 브랜치는 여기서 만들지 않습니다.

Hook: SessionStart matcher: startup .claude/hooks/session-start.sh
역할
· feat/pr-develop이 없으면 develop에서 새로 만든다
· 있으면 그쪽으로 체크아웃만 한다
· 세션 브랜치(feat/new-prompt-*)는 만들지 않는다 — 탐색·질문만 하는 턴이면 빈 브랜치가 남지 않도록 
# 핵심 로직
if ! git rev-parse --verify feat/pr-develop; then
  git checkout develop
  git checkout -b feat/pr-develop
fi
git checkout feat/pr-develop
2026-04-20 정책 변경 — 과거에는 SessionStart에서 세션 브랜치까지 선점 생성했지만, 빈 브랜치가 쌓이는 문제로 "지연 생성"으로 전환했습니다. 실제 Edit/Write가 발생하는 순간에만 만듭니다.
STEP 3 / 8 · PreToolUse

보호 브랜치 차단 + 세션 브랜치 지연 생성 (check-branch.sh)

Edit/Write가 발생하기 직전, 현재 브랜치를 검사해 자동 분기하거나 차단합니다.

Hook: PreToolUse matcher: Edit|Write .claude/hooks/check-branch.sh
분기 로직
  • feat/new-prompt-* → 그대로 허용 (exit 0)
  • feat/pr-develop → feat/new-prompt-YYYYMMDD-HHMMSS를 만들어 전환 후 Edit 허용
  • main / master / develop → exit 2로 차단
  • .claude/ 하위 파일은 어느 브랜치든 허용 (훅 자체 수정 목적)
case "$BRANCH" in
  feat/new-prompt-*) exit 0 ;;
  feat/pr-develop)
    SESSION="feat/new-prompt-$(date +%Y%m%d-%H%M%S)"
    git checkout -b "$SESSION"
    exit 0 ;;
  main|master|develop)
    echo "보호 브랜치에서 수정 불가" >&2
    exit 2 ;;
esac
이 지연 생성 전략 덕분에 질문·탐색만 하는 프롬프트에는 브랜치 변화가 0건입니다.
STEP 4 / 8 · PreToolUse · .env 차단

.env 파일 이중 방어

민감 정보가 LLM이나 커밋으로 새어나가지 않도록 두 단계로 막습니다.

Danger: secrets permissions.deny PreToolUse 인라인 훅
1차 — permissions.deny
settings.json의 permissions.deny에 Edit(**/.env), Write(**/.env)를 등록. Claude Code harness가 tool 실행 전에 즉시 거부합니다. 
"permissions": {
  "deny": ["Edit(**/.env)", "Write(**/.env)"],
  "ask":  ["Bash(git push:*)", "Bash(git push)"]
}
2차 — PreToolUse 인라인 훅
permissions를 우회하는 경로에 대비해 훅에서도 한 번 더 차단합니다. 
{
  "type": "command",
  "if": "Edit(**/.env)|Write(**/.env)",
  "command": "echo '.env 파일은 수정할 수 없습니다.' >&2 && exit 2"
}
추가로 Stop 훅의 자동 커밋 단계에서도 git reset -- '**/.env' '.env'로 스테이징을 해제합니다. 3중 방어.
STEP 5 / 8 · PostToolUse

저장 직후 즉시 Lint (post-lint.sh)

Write/Edit로 파일이 변경되면 확장자에 맞춰 linter를 돌리고, 경고를 additionalContext로 Claude에 전달합니다.

Hook: PostToolUse matcher: Write|Edit .claude/hooks/post-lint.sh
  • *.py → ruff check 실행
  • *.ts / *.tsx → frontend/node_modules/.bin/eslint 실행
  • 오류가 있으면 hookSpecificOutput.additionalContext로 lint 로그를 Claude 컨텍스트에 주입
  • 즉각 피드백 → Claude가 다음 턴에 스스로 수정
case "$FILE_PATH" in
  *.py)
    ruff check "$FILE_PATH" >/tmp/claude-post-lint.log 2>&1 || {
      jq -n --arg e "$(cat /tmp/claude-post-lint.log)" \
        '{hookSpecificOutput:{
           hookEventName:"PostToolUse",
           additionalContext:("⚠️ ruff 경고:\n"+$e)}}'
    } ;;
  *.ts|*.tsx)
    frontend/node_modules/.bin/eslint "$FILE_PATH" ... ;;
esac
PostToolUse는 경고 전달만 하고 차단은 하지 않습니다. 차단은 Stop 훅의 최종 lint가 담당합니다.
STEP 6 / 8 · Stop

최종 Lint + 자동 커밋 + 머지 알림 (auto-commit.sh)

매 프롬프트 턴 종료 시 실행되는 핵심 훅. 4단계를 순차 수행합니다.

Hook: Stop .claude/hooks/auto-commit.sh
1
안전망 분기 — pr-develop에 변경이 남아있으면 세션 브랜치로 자동 분기 (Bash 수정/.claude 예외 대응)
↓
2
Lint 게이트 — ruff → flake8 → py_compile, eslint → tsc. 실패 시 커밋 중단
↓
3
스테이징 + .env 해제 — git add -A 후 .env만 unstage
↓
4
한글 커밋 + 머지 질문 강제 — 경로 기반으로 카테고리 자동 감지(chore(backend+frontend)), 세션 브랜치면 decision: "block"으로 Claude를 다시 깨워 "pr-develop에 머지할까요?"를 질문하게 함
# 커밋 제목 자동 생성 예
chore(backend+frontend+hooks): settings.local.json, llm.py 외 9건

Co-Authored-By: Claude <noreply@anthropic.com>
STEP 7 / 8 · PostCompact

컨텍스트 압축 후 규칙 재주입 (post-compact.sh)

자동/수동 압축으로 핵심 규칙이 날아갔을 때, additionalContext로 다시 넣어줍니다.

Hook: PostCompact .claude/hooks/post-compact.sh
왜 필요한가?
컨텍스트가 자동 압축되면 Claude는 CLAUDE.md의 규칙 일부를 잊을 수 있습니다. 브랜치 규칙·머지 질문 강제·커밋 한글화 같은 절대 생략하면 안 되는 규칙을 훅이 다시 주입합니다. 
{
  "hookSpecificOutput": {
    "hookEventName": "PostCompact",
    "additionalContext": "
      ## 브랜치 규칙
      - 현재 브랜치: feat/new-prompt-20260424-XXXX
      - feat/pr-develop에서 직접 작업 절대 금지

      ## Stop 훅 머지 알림
      - block 알림이 오면 반드시 사용자에게 질문

      ## 개발 규칙
      - TDD 우선 (red → green → refactor)
      - 커밋 메시지는 반드시 한글
      - .env 파일 수정 금지
    "
  }
}
이것이 Claude에게 "매번 기억해" 라고 말하는 것보다 훨씬 신뢰도가 높은 이유입니다. 압축 직후 harness가 강제로 주입하므로 Claude는 잊을 기회가 없습니다.
STEP 8 / 8 · 전체 흐름

한 턴 동안 일어나는 일

프롬프트 제출부터 PR 생성까지, 훅들이 어떻게 맞물리는지 따라가 봅니다.

1
사용자 프롬프트 제출
↓
2
(탐색·질문만) 브랜치 변화 0. 빈 세션 브랜치 생성 안 됨.
↓
3
실제 Edit/Write 발생 → PreToolUse·check-branch.sh가 feat/new-prompt-* 자동 생성 + 전환
↓
4
파일 저장 직후 → PostToolUse·post-lint.sh가 ruff/eslint로 경고 피드백
↓
5
턴 종료 → Stop·auto-commit.sh가 lint 통과시키고 한글 커밋, "pr-develop 머지할까요?" 질문 강제
↓
6
사용자 승인 → Claude가 세션 브랜치 → pr-develop 머지
↓
7
git merge 감지 → PostToolUse·check-merge.sh가 "develop으로 PR 생성할까요?" 질문 강제
↓
8
PR 생성 → rebase → gh pr create --base develop (push는 permissions.ask로 사용자 승인 필요)
핵심 이점 — Claude가 규칙을 외울 필요가 없습니다. 훅이 차단하고, 알리고, 강제 질문을 만드니 절차가 일관되게 지켜집니다.
